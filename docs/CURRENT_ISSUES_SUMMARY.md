## 🔴 重大な問題（Critical Issues）

### 1. 日本語テキストの文字化け問題（未解決）

**現状**:
- カスタムフォントの登録が実装されていない（TODOコメントのみ）
- 非ASCII文字を含むテキストが標準フォント（Helvetica）で書き込まれる
- 警告ログは出力されるが、実際には文字化けが発生する

**技術的詳細**:
```136:143:src-tauri/src/commands/pdf_generator.rs
if font_manager::is_font_available("NotoSansJP") {
    // TODO: oxidize-pdfの実際のAPIに合わせて実装
    // 注意: 現時点では、カスタムフォントの登録が未実装のため、標準フォントを使用
    // これにより、日本語テキストが文字化けする可能性がある
    // 実装後は、Font::Custom("NotoSansJP".to_string())を使用する予定
    log::warn!("非ASCII文字を含むテキストを処理しますが、カスタムフォントの実装が未完了のため、文字化けする可能性があります: {}", 
        text_block.text.chars().take(50).collect::<String>());
    Font::Helvetica
```

**影響範囲**:
- 日本語を含むすべてのPDF保存操作
- ユーザーが期待する結果が得られない

**根本原因**:
- `oxidize-pdf`のAPIが未確認のため、カスタムフォントの埋め込み方法が不明

**推奨対応**:
1. `oxidize-pdf`のAPIドキュメントを確認
2. カスタムフォントの埋め込み機能を実装
3. フォントが利用できない場合は、エラーを返すか明確な警告をUIに表示

## 🟡 重要な問題（Important Issues）

### 2. PDF.jsオブジェクトのクリーンアップ関数の問題

**問題の詳細**:
- `useEffect`のクリーンアップ関数で`pdfDoc`を参照しているが、依存配列に含まれていない
- クリーンアップ関数が古い値を参照する可能性がある（クロージャの問題）

**該当コード**:
```507:523:src/components/PDFViewer.tsx
return () => {
  // why: pdfDocはuseStateで管理されているため、最新の値を参照するためにget()を使用
  // alt: pdfDocを依存配列に含める（無限ループが発生する可能性がある）
  // evidence: クリーンアップ関数内で最新のpdfDocを参照することで、正しくクリーンアップできる
  const currentPdfDoc = pdfDoc;
  if (currentPdfDoc) {
    try {
      currentPdfDoc.destroy();
    } catch (error) {
      // 既に破棄されている場合はエラーを無視
      if (import.meta.env.DEV) {
        console.warn('Failed to destroy PDF document on unmount:', error);
      }
    }
  }
};
}, [pdfStructure, renderPageNumber, renderAllPages, uiState.viewMode, setCurrentPageInStore]); // pdfDocはクリーンアップ関数内で参照するため、依存配列に含めない（無限ループを防ぐ）
```

**問題点**:
- `pdfDoc`が依存配列に含まれていないため、クリーンアップ関数が古い`pdfDoc`を参照する可能性がある
- `pdfStructure`が変更されても、古い`pdfDoc`が破棄されない可能性がある

**影響**:
- メモリリークが発生する可能性
- 古いPDFオブジェクトが残り続ける

**推奨対応**:
- `useRef`を使用して`pdfDoc`を管理し、クリーンアップ関数で最新の値を参照する
- または、`pdfStructure`が変更されたときに明示的に`pdfDoc`を破棄する

### 3. 同時編集操作の競合状態（部分的に未解決）

**問題の詳細**:
- `isLoading`フラグにより読み込み中の操作はブロックされるが、複数の編集操作が同時に実行された場合の順序保証は未実装
- 例: `resizeImage`と`moveImage`が同時に実行された場合、どちらが先に適用されるか不明

**該当コード**:
```224:270:src/stores/pdfStore.ts
resizeImage: async (imageId: string, width: number, height: number) => {
  try {
    set({ error: null });
    
    const state = get();
    if (state.isLoading) {
      throw new Error('PDFの読み込み中です。しばらくお待ちください。');
    }
    if (!state.pdfStructure) {
      throw new Error('PDFが読み込まれていません');
    }
    // ← この時点の状態を取得
    const updatedImage = await invoke<ImageElement>('resize_image', { ... });
    // ← この間に別の操作が実行される可能性がある
    set({ pdfStructure: updatedPdfStructure }); // ← 状態を更新
  }
}
```

**問題シナリオ**:
1. ユーザーが画像をリサイズ（`resizeImage`実行）
2. ユーザーが画像を移動（`moveImage`実行）
3. `resizeImage`が完了して状態を更新
4. `moveImage`が完了して状態を更新（`resizeImage`の変更が上書きされる可能性）

**影響**:
- ユーザーの操作が失われる可能性
- 予期しない動作が発生する可能性

**推奨対応**:
- 操作をキューイングする（順次実行）
- または、各操作で状態のバージョン管理を行う（楽観的ロック）
- または、操作のロック機構を実装する（編集操作中は他の操作をブロック）

### 4. メモリ使用量の問題（未解決）

**問題の詳細**:
- 画像データがbase64エンコードされた文字列として保持されるため、メモリ効率が悪い
- base64エンコードにより、元のバイナリデータの約33%増加
- 大きなPDFファイルをメモリに読み込む際のメモリ使用量が大きい

**該当コード**:
```33:33:src-tauri/src/models/pdf_structure.rs
pub data: String, // ← base64エンコードされた文字列
```

**計算例**:
- 10MBの画像 → base64エンコードで約13.3MB
- 100ページのPDF（各ページに1MBの画像）→ 約1.3GBのメモリ使用量

**影響**:
- 大きなPDFファイルを処理する際にメモリ不足が発生する可能性
- アプリケーションのパフォーマンスが低下する

**推奨対応**:
- 画像データをストリーミング処理する
- または、画像データを一時ファイルに保存し、必要時に読み込む
- または、画像データを圧縮する
